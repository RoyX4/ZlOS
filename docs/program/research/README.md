## Result

All 33 repositories are downloaded at recorded commits and represented exactly once in the source manifest and normalized matrices. The suite covers source, active build/registration paths, documentation, tests/CI, licenses, meaningful features, implementation strategies, gaps, false-green hazards, best idea donors, and a clean-room zl/zlOS integration architecture. A dedicated third pass inventories driver lifecycles and every meaningful application, service, utility, game, media, package and operations target. A fourth pass goes inside the visible product: design systems, desktops, interactions, browsers, exact app workflows, media/creative/game experiences, agent and operator interfaces, accessibility, localization, remote delivery, and the service/process machinery underneath. A fifth pass explains the actual fast-path mechanics behind responsive, polished systems and consolidates the whole destination into 906 stable product feature atoms. All passes separate local, submodule, fetched, third-party, disabled, stub, built, reachable and verified evidence.

This is an idea and behavior study. It does not import repository code into zl or zlOS.

The main conclusion is that no repository should become the zlOS blueprint. The best system is a deliberate combination:

- existing zl/zlOS hardware, storage, desktop, language, and self-hosting work stays the spine;
- Hyper contributes executable boot-contract testing;
- Brook contributes real-logic host testing; SerenityOS contributes broad host and x86-64 target-test verification plus multiarchitecture build/boot structure;
- RustOS contributes ownership contracts, failure-atomic reasoning, and honest failed evidence;
- NexiOS contributes explicit resource bounds and Skift contributes typed object/transfer questions; neither pinned transfer/revoke implementation is accepted as correct;
- MollenOS and LemonOS contribute generated service/protocol seams;
- Zinnia contributes narrow driver boundaries;
- SerenityOS contributes enforced isolation; LemonOS, banan-os, and duckOS contribute compositor/audio/service seams whose credential, ownership, and user-boundary failures are negative tests;
- Chitti contributes typed agent plans and attenuated grants, corrected by moving the model/orchestrator out of ring 0;
- snarkOS contributes explicit operational roles and lifecycle;
- mission-control contributes the public-QEMU lifecycle shape, corrected with real data-plane authentication and containment;
- ProtOS contributes a compact end-to-end user-space desktop slice, but primarily supplies hostile regression cases for ELF, usercopy, syscall, IPC, shared-memory, and lifetime safety.

## Most important negative findings

These are not generalized accusations; they are concrete source/build findings at the pinned revisions and are useful as zlOS regression shapes:

- build/test wrappers can manufacture green results by discarding failures or treating timeout as success;
- files, TODOs, screenshots, checked-in images, and test names do not establish reachability or runtime behavior;
- raw user pointers recur across syscall and IPC boundaries;
- ELF and archive loaders often lack an input length, checked arithmetic, complete header validation, permission validation, and failure cleanup;
- driver enumeration is repeatedly mistaken for usable hardware support;
- queues, waits, device polls, teardown, and service calls are often unbounded;
- read-only package bytes are repeatedly mistaken for process isolation;
- ambient global IDs and ring-0 loaders/orchestrators destroy otherwise good modular designs;
- control-plane tokens do not protect a separately unauthenticated VNC data plane;
- formal models, host builds, QEMU boots, and physical hardware runs are different evidence levels and must remain separate.

High-value concrete regressions include banan-os's `setreuid` privilege escalation; LemonOS's fork credential corruption and permissionless kill; Brook's unsafe usercopy and compositor-control surface; duckOS's shared-memory ownership bypass; hhuOS's unrestricted user MMIO mapping; Skift's channel free-slot inversion; NexiOS's missing source COPY check and truncated revoke; TacOS's negative syscall index, ELF permission inversion, and segment overflow; NyauxKC's PCI coordinate reversal and corrupt USTAR payload import; Cyjon's failure-masking build and user-triggerable global halt; AthenX's accept-all credential validator; Banana OS's unprivileged ring-0 module loader; mission-control's enumerable unauthenticated VNC sockets; MaslOS-2's lengthless/zero-step ELF relocation path; ProtOS's inverted ELF magic/null syscall/use-after-free paths; snarkOS's zero REST-rate division; and vib-OS's disconnected or simulated feature claims.

## Integration order

The full destination is retained, but its dependencies are explicit:

1. preserve and inventory current evidence;
2. finish retained client/shell surfaces and measured frame/input behavior;
3. create bounded asynchronous block I/O and crash-consistent zlfs;
4. establish real 64-bit processes and a hostile-user boundary;
5. add typed handles, zlIDL, supervision, and sessions;
6. migrate system services without deleting proven fallbacks;
7. prove real wired networking and split browser processes;
8. move applications into processes and add reproducible packages;
9. deepen driver lifecycle, audio, and load-bearing Intel composition;
10. converge zl on system-grade ABI, native, executable, and relocatable output;
11. add capability-native agents and signed tools;
12. deploy a hardened public demo service;
13. rebuild the matching toolchain/system inside zlOS and then prove later architectures.

The exact build products and exit conditions are in the integration plan. Staging does not redefine the target as a deliberately small MVP.

## Evidence boundary

The suite is exhaustive at the level of meaningful features and implementation strategies for the pinned trees; it is not a claim that every branch, historical release, generated dependency, application asset, or individual helper function was executed. A source audit can establish mechanisms and defects but cannot turn unrun QEMU or physical paths into runtime proof.

The weakest link is graphical and hardware runtime coverage: only explicitly marked local builds/tests ran here, and several major systems remain source/test/CI audits. The matrix and plan preserve that boundary instead of averaging everything into a misleading maturity score.
