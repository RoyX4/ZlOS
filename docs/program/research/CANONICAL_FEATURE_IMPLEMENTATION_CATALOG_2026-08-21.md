# Canonical feature and implementation-pattern catalog

Date: 2026-08-21

Scope: the complete normalized feature vocabulary extracted from the 33 pinned starred repositories, the detailed/refutation audits, the earlier Lunaris comparison, and the current zl/zlOS architecture. This is the layer below the repository matrix: each row is one capability or engineering obligation, the strongest observed implementation families, the recurring failure shape, and the clean-room zl/zlOS contract.

This catalog transfers ideas, contracts, tests, and questions. It does not transfer source code. Repository names identify provenance; evidence strength remains in the linked dossiers and [`ALL_33_FEATURE_MATRIX_2026-08-21.md`](ALL_33_FEATURE_MATRIX_2026-08-21.md).

## How to use it

- A feature is not complete because its row exists. It advances through `claimed -> source -> reachable -> built -> booted -> scenario -> hardware` with exact receipts.
- “Best input” means best observed question/pattern, not an endorsement of the whole project.
- “Reject” is part of the specification. Most important lessons came from a strong seam paired with a concrete unsafe implementation.
- The zlOS contract column is behavior to specify independently in zl/zlOS conventions.
