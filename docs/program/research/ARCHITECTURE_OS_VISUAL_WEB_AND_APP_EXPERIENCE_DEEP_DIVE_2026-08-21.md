# Architecture OS visual, web, and application experience deep dive

**Snapshot date:** 2026-08-21
**Scope:** ChittiOS, NexiOS, RustOS, Zinnia, Skift, Fudge, TacOS, NyauxKC, and Cyjon/Fern-Night
**Question:** What do these systems actually look like, how do their visible interactions work, what user workflows really exist, what is local versus fetched or external, and what should zlOS learn without copying their code?

This is a source-and-artifact audit, not a screenshot beauty ranking. It traces visible claims through assets, UI source, app manifests, build graphs, boot configuration, protocols, tests, and checked-in evidence. A launcher label is not automatically an app. An icon allowlist is not automatically a product. A README screenshot is not automatically generated by code in the repository. A dependency named in a lockfile is not local implementation.

## Bottom line

There are four materially different product models in this shelf:

1. **ChittiOS is an agent console that grew into an operating environment.** It has by far the broadest locally inspectable app surface and the only substantial local browser engine. Its strongest product idea is not its enormous feature count; it is the shared grammar joining agent intent, capability manifests, app-specific visual surfaces, deterministic tools, and one coherent console shell.
2. **RustOS is a compositor and desktop-systems proof.** It has the most deliberate local visual language, the best locally inspectable window/compositing architecture, and unusually serious render scheduling. Its consumer app catalog is almost empty. The polish is real; the “desktop product” breadth is not.
3. **Fudge and Cyjon/Fern-Night are compact desktop stacks with useful architectural ideas.** Fudge's mailbox-carried declarative UI is the cleanest reusable systems idea in the conventional desktops. Cyjon/Fern-Night has a working-looking taskbar/window protocol and alpha compositor, but its application menu is substantially stale. TacOS is much smaller, yet its keyboard-controlled pointer and simple shared-buffer window protocol are memorable.
4. **NexiOS, Zinnia, and NyauxKC are not local desktop products in these snapshots.** NexiOS has a framebuffer terminal and visual demo. Zinnia's attractive README desktop is external userland. NyauxKC has a branded Limine boot background and a Flanterm kernel console. Counting any of those as locally implemented desktop shells would be false.

**Skift needs its own warning label.** It has the richest historical design lineage and an elegant local shell/compositor adapter, but most of the advertised KarmUI, Hideo applications, game bundles, and Vaev web implementation are pinned/fetched projects absent from this checkout. Its dated screenshots are excellent design references, not proof of the current local tree.

The best clean-room synthesis for zlOS is therefore:

- RustOS's render/compositor discipline and coherent tokenized visual direction;
- ChittiOS's capability-aware app/agent contract, app catalog breadth, searchable shell, and progressive browser pipeline;
- Fudge's declarative UI messages and typed service boundaries;
- Skift's immutable UI mental model, damage-driven compositor contract, and concise launcher taxonomy;
- Cyjon's proportional taskbar entries, Alt-Tab path, transparent surfaces, and process-owned shared windows;
- TacOS's keyboard-pointer fallback and minimal client/server window contract;
- explicit proof labels and external-boundary honesty learned from Zinnia, NyauxKC, and the stale parts of Skift/Cyjon.

## Evidence and boundary rules

### Evidence labels

| Label | Meaning in this report |
|---|---|
| **C** | A README, design document, screenshot, or other checked-in claim. |
| **S** | Directly present in source, manifest, config, or asset code. |
| **R** | Connected to a normal boot/build/manifest path in the inspected snapshot. |
| **T** | A relevant automated or checked-in qualification path was identified. |
| **B** | A build had already been completed in the broader repository survey; this report did not repeat it. |
| **Q** | Runtime behavior directly observed in this audit. |
| **H** | Physical-hardware behavior directly observed in this audit. |

No section below adds **Q** or **H**. Visual inspection of an image is **C**, not runtime verification. Source inspection is **S**. A build graph can establish **R** while the resulting runtime remains unobserved. Earlier narrow build evidence exists for the NexiOS kernel/ISO and Zinnia workspace, but it does not prove the graphical experience.

### Product-boundary vocabulary

- **Local:** implementation is in the named repository snapshot.
- **Gitlink/submodule:** a separate repository pinned by the parent. Cyjon's Fern-Night userland is in this category, though its pinned checkout was available and audited.
- **Fetched source:** a build/project lock names an external project and commit, but its implementation is absent from the local snapshot. Skift's main UI/app ecosystem is here.
- **Bundled external content:** data ships with the system but is not the project's original code, such as game WAD data.
- **External userland/product:** the screenshot or workflow relies on a separate project not included in the kernel repository, as with Zinnia's bootstrap image.
- **Historical/removed:** present only in dated screenshots, idea lists, or a `removed/` tree; it is not current reachable product surface.

## 1. ChittiOS: agent workstation as the shell

### Visual language and configuration

ChittiOS has the clearest documented product identity. `DESIGN.md`, `README.md`, `kernel/src/ui/`, `configs/core/ui.json`, and the checked-in media agree on a warm, editorial console rather than a generic neon hacker terminal.

The programmatic Synapse C mark is a terracotta open ring (`#cc785c`) with a cream node (`#f5efe6`/`#faf9f5`) on warm ink. The boot sequence draws that mark, holds the splash for roughly 1.3 seconds, then reduces it to a small status glyph. The principal semantic colors are:

| Role | Values |
|---|---|
| Primary | `#cc785c`; active `#a9583e`; disabled/hairline `#e6dfd8` |
| Ink/body | `#141413`, `#252523`, `#3d3d3a` |
| Muted | `#6c6a64`, `#8e8b82` |
| Canvas/surfaces | `#faf9f5`, `#f5f0e8`, `#efe9de`; dark `#181715`, `#252320`, `#1f1e1b` |
| Accents/status | teal `#5db8a6`, amber `#e8a55a`, success `#5db872`, warning `#d4a017`, error `#c64545` |

The console atlas and browser font stack are distinct. Geist Mono is the console identity, and `DESIGN.md` documents an ASCII atlas. The browser tree also carries true TTF/WOFF assets: Noto Bengali, CJK, Devanagari, Emoji, Gujarati, Gurmukhi, Kannada, Malayalam, Tamil, and Telugu, plus Ubuntu Mono and Font Awesome. That is meaningful international text coverage in assets and shaping, but it is not evidence of localized ChittiOS product strings.

`configs/core/ui.json` makes presentation a data surface rather than a rebuild. `/ui reload` applies it. Theme workflows include `/theme set`, `/theme save`, and `/theme install`; presets include dark, light, Solarized Dark, Nord, Dracula, and Ubuntu. Wallpaper can be disabled, generated as a gradient, loaded from a local path, or fetched from an HTTPS URL. Cover scaling, opacity/transparency, cursor colors or bitmap sprites, syntax colors, font, and font size are configurable. TUI surfaces blend over the wallpaper. Status templates can interpolate version, date/time/timezone, model, architecture, uptime, and brand values, and the status region can be placed at the top, bottom, left, or right.

This is the best theme architecture in the shelf because the controls reach beyond colors into density, pane proportions, typography, cursor, wallpaper, status placement, and syntax. Its weakness is discoverability: a configuration language and slash commands are powerful, but they are not yet the same thing as a previewable, reversible Settings experience.

### Workspace interactions

The visible environment is a resizable split between a chat pane and an action pane, not a freeform overlapping-window desktop. Configuration controls `chat_pct`, `font_scale`, pane order, titles, splash, and status templates. The action side is tabbed and hosts trace output, process views, todo lists, editor documents, and image/audio/video or application surfaces.

The shell supplies:

- a composer with slash-command and `@file` suggestion menus;
- a searchable command browser;
- selection, syntax highlighting, OSC52 clipboard copying, and bracketed paste;
- live clock/status material;
- toasts and notifications;
- permission modals;
- focus and cursor state;
- bounded panes, tabs, text views, surface views, menus, and modal layers.

Those are not README-only aspirations: the framebuffer modules split across `clock`, `colors`, `composer`, `console`, `cursor`, `focus`, `layout`, `menu`, `modal`, `paint`, `pane`, `select`, `status`, `surface`, `tabs`, `text`, `toast`, and `views` under `kernel/src/ui/` **[S/R]**. The checked-in `docs/media/10-agents.png` shows the design in context: warm dark canvas, terracotta borders/selection, top system status, Shell Agent tab, searchable Agents modal, row status icons, keyboard hints, and the bottom composer **[C]**.

Application canvases use a deliberately tiny drawing protocol. Apps paint into bounded 256×192 logical surfaces using operations such as clear, rectangle, line, and pixel. The shell scales or letterboxes the result. Board games use `board_set`/`board_mark`; while a model turn is running the UI shows a loader strip and rejects more input. There is no text drawing operation in the surface DSL, so document-centric applications fall back to editor tabs. This is a strong containment mechanism, but it also makes rich native widgets, semantic accessibility, adaptive typography, and responsive layouts difficult.

### Browser: real local engine, bounded parity

ChittiOS is the only system here with a substantial browser implemented in the audited local tree. Its `no_std` Rust pipeline is visibly staged:

`HTML parse → script/bytecode setup → event loop → CSS → layout (flow/flex/partial grid) → paint`

Loader, CORS, cookies/storage, iframe messaging, events, Page WASM, SVG/MathML subsets, and workers sit around that path. The body limit is 1 MiB. Loading progresses through DOM, CSS, scripts, and images; the action pane paints actual pixels 1:1 and exposes progress and wait-cursor state.

User and agent workflows include open/navigate, back, scroll, coordinate click, status, link enumeration, and text extraction. No corresponding forward tool was found. Human interaction includes drag selection, highlight and OSC52 copy; forms retain control values; history, cookies, localStorage, sessionStorage, cache, CORS/preflight, external styles and scripts, one level of CSS `@import`, background images, nested iframes to depth two, first-frame video, Canvas2D, DOM events, `fetch`, link/click/form navigation, and persistent JavaScript state with execution budgets. Native fallback handlers cover common Radix-like switch, accordion, and tabs patterns.

The limitation list matters as much as the feature list. Source explicitly rejects Chrome parity. There is no native-code JIT, complete CSS Grid auto-placement, full SVG filter/SMIL, or complete MathML. Several Page WASM host imports return `ENOSYS`; the JavaScript `WebAssembly` object exposes empty export stubs; `sendBeacon` returns success without transmission; some focus/blur/click/scroll paths and `window.scrollTo`/`requestAnimationFrame` are no-ops; module namespace imports are unsupported; unsupported ECMAScript is skipped best-effort. The browser also runs in the kernel, so every parser, decoder, layout path, and script interpreter enlarges the trusted computing base.

The clean-room lesson is to keep its staged, inspectable progressive-render pipeline and agent-readable tools, but put the engine in a capability-limited user process. “Can the model see links and click?” and “Can an untrusted page corrupt the kernel?” must have different architectural answers.

### Standout ideas and gaps

**Keep the idea:** one searchable shell grammar across human commands, agent tools, apps, and files; theme/status configuration as data; capability-declared packages; bounded paint surfaces; deterministic tools behind model planning; progressive browser visibility.

**Fix before adopting:** move browser/media/document parsers out of the kernel; add semantic UI nodes and a text primitive; make Settings preview and rollback theme changes; add a forward-navigation contract; separate “manifest reachable,” “loads,” and “workflow complete” badges. Known system gaps also affect visible reliability: orchestrator kill can be trace-only, install/uninstall is not transactional, capability revocation can miss an already-created execution snapshot, and package trust/signature naming is ambiguous.

## 2. NexiOS: capable shell, diagnostic presentation

### What it looks like

NexiOS does not contain a desktop, window manager, pointer shell, browser, widget toolkit, wallpaper/theme service, or graphical app framework in this snapshot. Its local visual product is a framebuffer terminal **[S/R]**:

- black main background;
- 8×16 bitmap font covering printable ASCII 32–126;
- newline, carriage return, tab, backspace, and scroll implemented by framebuffer movement;
- fixed bottom status region;
- status background `#0D1117`, two-pixel top separator `#30363D`, left text `#C0C0C0`, and right text cyan `#00AAFF`;
- build identity differentiating debug/release.

Terminal colors are selected programmatically. No ANSI escape parser, insertion cursor, user theme file, semantic text selection, history widget, or accessibility layer was found in the terminal path. The status bar is useful because it makes the kernel image feel like a deliberate appliance rather than undifferentiated boot logs, but the layout is fixed.

The visual demo replaces the terminal at a hardcoded 1024×768 resolution with a Mandelbrot rendered using a 16-color VGA-like palette in 2×2 blocks. A key returns from the fractal. A subsequent three-second “spinning rectangle” is really four 7×7 colored corner markers—red, green, blue, yellow—cycled as a simple animation before the terminal is restored. Source strings mix German (“gerendert”, “Taste druecken”, “Rotation fertig”) with English shell text. There is no locale switcher or resource catalog, so this is incidental bilingual text, not localization.

### User workflows

The product depth is in its shell, not its visuals. The static registration table contains 61 shell entries. Meaningful groups include:

- **orientation and control:** help, clear, echo, version, uptime, tasks, memory information, kernel log, reboot, shutdown, and self-test;
- **program/process work:** run, run ELF, background launch, cancel, jobs, wait, trap, limits, program and driver management;
- **filesystem:** current directory, directory stack, list, cat, less/more, touch, basic VFS commands;
- **shell language:** environment export/set, aliases, history, source, read, printf, test, shift, sleep;
- **network/hardware inspection:** `ifconfig`, ping, PCI listing, and related status commands;
- **user binaries:** `init`, `vfsd`, `iocd`, `sh`, `cat`, `ls`, `mkdir`, `rm`, `more`, `touch`, and the graphical demo.

This is more complete as a monitor/shell environment than its appearance suggests. It is still not an “apps” desktop: commands share the same terminal and no local app chrome, launcher taxonomy, file previews, media surface, or web renderer exists.

### Underneath, standout, and gaps

The framebuffer terminal owns line layout and scrolling; the demo bypasses it and writes pixels directly; shell functions are statically registered rather than discovered from desktop metadata. This makes boot and qualification deterministic, but it also couples the UI to one low-level surface.

**Keep the idea:** a permanent, compact system-status rail is excellent for an experimental OS, especially when every graphical layer can fail. The demo's explicit save/replace/restore pattern is also a useful smoke-test contract.

**Do not mistake for a desktop:** no local icons, themes, wallpaper, responsive geometry, pointer, a11y, localization, browser, media workflow, or app lifecycle UI exists. Earlier work established a narrow kernel/ISO build **[B]**; no runtime graphical claim is added here.

## 3. RustOS: strongest local desktop visual system, thinnest consumer catalog

### Aurora dark visual system

RustOS's current source calls its direction “Aurora dark.” The palette is unusually coherent for a small OS:

| Role | Values |
|---|---|
| Sky | top `#141A3C`, middle `#0C0E2A`, deep `#050816` |
| Aurora | cyan `#4A8FFF`, violet `#A367FF`, mint `#6CF0C2` |
| Stars | `#E0E8FF` |
| Glass | dark `#0F1430`, deep `#080C1F`, border `#2A345A` |
| Accents | mint `#6CF0C2`, lavender `#A68BFF`, peach `#FF8D75`, gold `#FFD06C`, cyan `#6CE0FF`, pink `#FF7AC6` |
| Text | primary `#F1F5FF`, dim `#8E9CC0` |

The generated background is a three-stop vertical gradient with dimension-relative radial aurora washes and a deterministic starfield. Startup first presents a cheap gradient, then a worker builds the full background and yields every 16 rows. That is a real perceived-performance tactic: show a coherent first frame, refine without blocking the compositor.

Glass rails use an upper sheen, lower settled layer, inner bloom, one-pixel specular edge, and stepped shadows. Focus adds accent overlay. Chrome uses Rajdhani SemiBold; terminals use Iosevka Term. Source geometry constants establish a recognizable spatial rhythm:

- top rail at y=12, height 48;
- taskbar with 14-pixel bottom margin, height 64;
- side rail margin 24;
- desktop margins 36×24;
- launcher icons 32 pixels with 10-pixel gaps;
- taskbar icons 44 pixels with 12-pixel gaps;
- window radius 12, title height 36, content padding 16/14, six shadow steps;
- 18-pixel window controls, 10-pixel gaps, 14-pixel right inset;
- default window 720×460, minimum 360×240;
- new-window cascade 36×32 over six slots.

The checked-in UI architecture document still uses “Translucent Aero Palette” and in places describes a more monochrome blue system. Current `colors.rs` and background/chrome source are multiaccent Aurora. This is documentation drift, not two simultaneously proven themes.

App icons are procedural: an accent rounded tile, top highlight, and deterministic primitive glyph derived from the title. Special mappings exist for terminal, files, browser, settings, and music. Only Terminal is a real corresponding consumer app in this snapshot. A Browser icon recipe is not evidence of a Browser executable.

### Shell, windows, Wayland, and rendering

The user-space `uiserver` owns the framebuffer, desktop chrome, console-hosted windows, and a Wayland compositor. The visible interaction set includes:

- click the top launcher to asynchronously start a desktop entry;
- click taskbar entries to restore/focus console or Wayland windows;
- focus and reorder windows;
- drag by the title region;
- close, minimize, and toggle maximize through chrome controls;
- focused underline versus running dot in the taskbar; minimized icons render with alpha 150;
- route mouse/keyboard into the active Wayland client;
- standard socket `/run/user/1000/wayland-0`;
- maintain canonical surfaces, shared-memory buffers, frame callbacks, release, damage, and one final present.

No window-edge resizing path was identified in the local server, so “resizable desktop” should not be inferred from having minimum/default sizes. Maximize toggle is present.

## 6. Fudge: declarative mailbox UI on a compact dark desktop

### Visual grammar

Fudge's window manager fills the root `#202020` and draws a permanent menu bar with two selects:

- **Fudge:** About, Settings, Reboot;
- **Apps:** Shell, File Manager, Calculator, Test.

The design is static, dark, and utilitarian. Terminus PCF normal/bold fonts are available at 12, 14, 16, and 18 pixel sizes selected using display factor. Widget colormaps define normal, hover, and focus triplets. Typical surfaces use translucent black or dark gray (`#101010`, `#2A2A2A`, `#484848` and nearby values), white text, dusty red focus (`#805050`), and pale rose emphasis (`#E0B0B0`). Many ARGB values use alpha `E8`; focused window accents use additional translucent overlays.

Geometry is similarly direct: minimum window 320×200, 24-pixel border/header region, 32-pixel close area, and common eight-pixel padding/gap. These are repeated constants and per-widget arrays, not a semantic token service. The result is internally legible but expensive to theme or audit globally.

There is no wallpaper, icon theme, visual app identity, dock/taskbar, animation framework, shadow/radius language, or responsive breakpoint system. The desktop is better understood as a coherent debug workstation than as a styled consumer shell.

### Declarative widgets and interaction

The standout architecture is the UI message grammar. Apps send text describing a tree; the window manager parses types including button, choice, fill, image, layout, listbox, panel, select, text, textbox, textbutton, and window. Attributes cover color, cursor, display, flow, horizontal/vertical alignment, IDs and parents, label, MIME type, mode, click query, overflow, padding, source, spacing, span, weight, and wrapping.

Apps can subsequently send incremental tree commands—add, change, and remove—rather than linking the window manager's widget implementation into each process. Widget states are normal, hover, focus, and destroyed. The WM performs layout, text selection marks, scrollable list/text boxes, focus/hover damage, and partial redraw.

Pointer workflows are unusual but complete enough to use:

- left drag moves the focused window;
- right drag resizes the whole focused window, respecting the minimum size;
- wheel scrolls list/text surfaces;
- close sends both WM-close and termination messages;
- selects open menu-like choice lists;
- click query strings flow back to the owning actor.

Right-drag resizing avoids edge hit-testing and handles, but it is almost impossible to discover without documentation. There is no visible resize affordance or richer snap/maximize/minimize model.

The system model underneath is typed actor mailboxes. The UI process connects to keyboard, mouse, and video services and receives events; applications own intent/state while the WM owns parsing, placement, drawing, and input routing. That is a remarkably clean isolation boundary for a small OS.

## Clean-room integration plan for zlOS

This section intentionally translates behaviors and system shapes, not source code. It assumes zlOS wants the whole architecture and app destination, delivered in stages, rather than a deliberately crippled endpoint.

### 1. Pick one product thesis

The shelf shows that “desktop OS” is too vague to guide design. RustOS optimizes for compositor proof; ChittiOS for agent-mediated work; Skift for a modern app ecosystem; Fudge for message-oriented simplicity. zlOS should state its own invariant:

> **zlOS is a direct-manipulation desktop where every operation can also be inspected, composed, and safely invoked by an agent. Human UI and agent tooling are two projections of the same typed action model.**

That avoids two bad outcomes: bolting a chat panel onto an unrelated desktop, or forcing every human task through chat. Files still has folders, Browser still has tabs, Settings still has controls, and windows still drag. Each exposes the same action/state contracts to automation.

### 2. Layer the visible system

```text
Apps: Files Browser Terminal Settings Media Notes Mail Calendar Games Dev tools
                         │
               semantic app/UI protocol
                         │
Shell: launcher search notifications taskbar workspaces quick settings agent surface
                         │
     compositor: surfaces input focus damage frame scheduling capture
                         │
services: app registry permissions files network media text locale accessibility agent broker
                         │
              drivers/kernel/display/input/storage/network
```

The crucial boundaries are:

- **Kernel:** devices, isolation, memory, scheduling, filesystem/network primitives. No HTML, image codec, PDF parser, JavaScript runtime, or app widget parser.
- **Compositor:** buffers, surfaces, focus, input routing, damage, frame callbacks, capture, workspaces, window placement. It does not know what a “mail message” is.
- **Shell:** desktop chrome and policy—launcher, taskbar, notification center, quick settings, overview, permissions, agent activity, crash/restore UX.
- **UI service/toolkit:** semantic widgets, layout, text shaping, accessibility tree, design tokens, input methods, localization. Fudge proves message-carried trees can be small; Skift proves immutable views and damage can be clean.
- **App registry:** the only source of truth for installed/reachable app metadata. Menus and search are generated from it, preventing Cyjon-style dead launchers and RustOS-style icon recipes from being mistaken for apps.
- **Agent broker:** a user-space policy service. It exposes typed app actions and read models, asks for capability grants, logs receipts, and never gives a model raw kernel authority.
- **Browser service:** renderer processes and network/storage brokers separated from the shell and kernel. Agent tools use a semantic page view and explicit actions, not unrestricted framebuffer clicking as the primary path.

### 3. Build a real design-token system

ChittiOS demonstrates breadth of configuration; RustOS demonstrates coherence. Combine them by making tokens structured, semantic, and live-previewable.

#### Foundation tokens

| Family | Required fields |
|---|---|
| Color | canvas, surface levels 0–4, glass, border subtle/strong, text primary/secondary/disabled/inverse, accent roles, success/warning/error/info, selection, focus ring |
| Typography | UI family, document family, mono family, sizes, line heights, weights, tracking, fallback stacks per script |
| Space | 2/4/6/8/12/16/24/32/48/64 rhythm, content density multiplier |
| Shape | control and window radii, border widths, focus thickness, shadow/elevation recipes |
| Motion | fast/normal/slow durations, easing, spring values, reduced-motion alternatives |
| Layout | panel/taskbar dimensions, minimum touch targets, window minimums, breakpoints, safe areas |
| Media | wallpaper mode, cover/contain/crop, blur/dim, translucency strength |

#### Semantic component tokens

Buttons, fields, menus, cards, title bars, taskbar entries, tabs, notifications, modals, tooltips, lists, tables, document canvas, code editor, browser chrome, and agent permission cards each need normal/hover/pressed/focused/disabled/busy/error states. Hardcoding Fudge-style color triplets inside every widget makes later high-contrast and dark/light parity unnecessarily dangerous.

#### Theme contract

A theme is signed/validated data, not arbitrary code. It may select tokens, font assets, wallpaper, cursor, system sounds, and icon pack. Applying a theme starts a timed preview with **Keep** and **Revert**. Accessibility constraints can override unsafe theme values. Export/import records the schema version. The Settings UI edits the same data that command/agent tools use.

The first official direction should be coherent rather than maximal. RustOS's aurora demonstrates the value of authored atmosphere, but zlOS should not clone its navy/violet palette. Use zlOS's own north-star references, then validate every shell surface in QEMU screenshots at multiple modes and sizes.

### 4. Shell interaction inventory

The complete destination shell should include:

- searchable launcher over installed apps, actions, recent documents, settings, and commands;
- taskbar/dock showing running, active, minimized, attention, progress, and multiwindow states;
- window focus, raise, title drag, eight-edge resize, minimize, maximize/restore, close, snap halves/quarters, and keyboard tiling;
- overview with windows and workspaces;
- Alt-Tab and app-scoped window cycling;
- keyboard pointer fallback inspired by TacOS, plus full semantic keyboard navigation;
- quick settings for network, sound, brightness/display, input, accessibility, theme, and power;
- notification center with actionable, grouped, expiring, silent, and persistent notifications;
- global status/command palette useful even when the graphical shell is degraded;
- clipboard history and drag/drop contracts;
- permission prompts that name app, operation, target, duration, and data leaving the machine;
- crash surfaces offering reopen, safe mode, report, and inspect logs;
- lock/session switcher and onboarding;
- optional agent panel showing current plan, requested permissions, tool actions, and receipts without monopolizing the desktop.

Every visual control must have a direct input path, keyboard path, semantic action name, and agent-callable path where safe. The keyboard and agent paths must not simulate pointer coordinates when a semantic operation exists.

### 5. App model and catalog

An installed app record should carry:

- stable ID, human name, summary, icon, categories, executable/service endpoint;
- declared document/MIME handlers and deep links;
- window roles and single/multi-instance policy;
- capabilities with scope, purpose, duration, and revocation behavior;
- actions with typed inputs/outputs and confirmation policy;
- background/autostart justification;
- localization bundles and accessibility conformance metadata;
- package/source boundary: local, ported, fetched, bundled content;
- build artifact hash and qualification receipt.

The registry must validate that every launcher target exists in the installed artifact. UI should distinguish **installed**, **available to install**, **experimental**, **diagnostic**, and **historical**. It should never silently show a dead action.

### 6. Browser and web architecture

ChittiOS provides the best feature reference but the wrong privilege boundary. A zlOS browser should use:

```text
Browser chrome app
  ├─ profile/history/download service
  ├─ network broker (DNS/TLS/HTTP/cache/CORS/cookies)
  ├─ renderer process per site group
  │    ├─ HTML parser + DOM
  │    ├─ CSS cascade/layout/paint
  │    ├─ JS/WASM runtime with budgets
  │    └─ image/font/media decoders in further sandboxes where practical
  └─ agent page bridge (semantic read model + typed actions)
```

The first-class browser feature contract should explicitly track:

- navigation: back, forward, reload/stop, redirects, same-document navigation, history;
- HTML/forms: focus, selection, labels, validation, form submit, file picker mediation;
- CSS: cascade, fonts, flow, flex, grid, position/sticky/fixed, media queries, overflow;
- scripting: events, timers, promises, modules, workers, `fetch`, storage, WebAssembly;
- media: images, SVG, audio/video, Canvas, safe codec isolation;
- platform: cookies, cache, local/session storage, CORS/CSP, permissions, downloads;
- accessibility: generated semantic tree, names/roles/states, keyboard order, zoom/reflow;
- agent: page summary, links/controls/forms, read selected region, click/activate by stable semantic handle, fill/submit with confirmation, download receipt;
- safety: renderer crash recovery, memory/CPU/time quotas, origin isolation, capability broker, no raw kernel objects.

Every unsupported surface returns an explicit capability/error state. Chitti's best-effort skip is useful for keeping a page alive, but invisible no-op APIs such as fake-success beacon or focus calls make both users and agents misjudge completion. The browser UI should show degraded-page diagnostics without overwhelming normal browsing.

### 7. Agent UI architecture

ChittiOS's major insight is that the model is an untrusted planner behind deterministic tools. zlOS should generalize that to every app:

1. User states an intent in chat, command palette, voice, or an app-local “Ask” surface.
2. Agent broker resolves app actions and current semantic context.
3. A plan is rendered in plain language with risky or external steps marked.
4. Permissions are granted per action/target/duration, not as permanent blanket access.
5. Deterministic services execute bounded operations.
6. Apps expose progress and intermediate artifacts.
7. Independent checks validate output/state.
8. The shell records a receipt: request, actions, data touched, result, failures, and reversible steps.

The agent should be able to open Files and highlight the affected directory, navigate Browser through semantic controls, draft in Writer, and configure Settings through the same typed actions a human triggers. It should not forge UI clicks, directly mutate app internals, or claim completion because a tool call was attempted.

Visible agent states need their own design tokens and interaction rules: listening, planning, awaiting permission, running, blocked, verifying, complete, failed, cancelled. Busy state should never silently drop input as Chitti board apps do; queue, cancel, or clearly reject with a reason.

### 8. Accessibility and localization are architecture

Do not defer these to theme polish. The shared UI protocol must include:

- role, accessible name/description, value/state, relations, actions, live-region priority;
- deterministic focus order, focus restoration, skip regions, keyboard shortcuts, input modality;
- text zoom and UI scale independent of display resolution;
- high contrast, color-independent status, reduced transparency, reduced motion;
- pointer target minimums and alternatives to drag-only interactions;
- screen-reader service and braille/output adapter boundary;
- locale-keyed strings, plural/date/number/currency formatting, RTL mirroring, input methods;
- per-script fallback and shaping rather than a Latin bitmap-font assumption.

Chitti's multilingual fonts are a good asset start. TacOS's keyboard pointer is a good recovery path. Neither substitutes for semantics.

### 9. “Cool feature” shortlist worth prototyping

These are the most distinctive shelf ideas when stripped of project-specific styling:

1. **Semantic universal palette:** Chitti's slash/file suggestions expanded to apps, settings, documents, actions, and agent tools.
2. **Inspectable live status edge:** Chitti's templated system rail, switchable among compact top/bottom/side modes.
3. **Asynchronous authored background:** RustOS's cheap first frame followed by refined atmosphere, with reduced-motion/transparency variants.
4. **Deterministic procedural fallback icons:** RustOS's title-derived glyphs used only when an app has no supplied icon, visibly marked in developer tools.
5. **Window protocol simulator:** Skift's tiny create/attach/flip/move/resize/snap contract exposed in a developer Zoo app.
6. **Mailbox UI inspector:** Fudge's declarative tree visualized live, including app owner, semantics, damage, and action messages.
7. **Keyboard pointer/recovery mode:** TacOS's idea made discoverable in accessibility/quick settings and expanded with acceleration and click variants.
8. **Alt-anywhere move/resize:** Cyjon's move interaction paired with Alt+right-drag resize and visible overlay geometry.
9. **Proportional taskbar labels:** Cyjon's text-preserving window slots as an optional “wide taskbar” mode, alongside icon mode.
10. **Capability attenuation lab:** Chitti's Sandbox Lab turned into a system app showing exactly what an app/agent can see and how revocation changes it.
11. **Progressive page inspection:** Chitti's DOM/CSS/script/image stages surfaced in Browser diagnostics and agent receipts.
12. **Qualification games:** WayClick and classic board games used as permanent compositor/input/audio/save-state test workloads, not discarded demos.

### 10. Failure patterns not to inherit

- **Dead UI:** Cyjon's menu launches removed programs. Generate UI from packaged artifacts and test every action.
- **Icon fiction:** RustOS maps browser/files/settings/music icon glyphs without those apps. Keep fallback icon code separate from installed metadata.
- **Screenshot laundering:** Zinnia's external userland and Skift's history can be mistaken for current local features. Stamp screenshot, commit, artifact, boundary, and runtime environment.
- **Wishlist inflation:** Skift's ideas file is not a feature list. Maintain separate proposed, implemented, build-reachable, and runtime-verified states.
- **Fake protocol success:** Chitti's no-op APIs can tell callers success without effect. Unsupported operations must return explicit errors.
- **Kernel feature gravity:** Chitti's browser richness expands the kernel TCB. Rich parsers belong in isolated user space.
- **Static settings theater:** Fudge shows settings choices without proven application/persistence. Controls must display effective state and verify change.
- **Invisible gestures:** Fudge's right-drag resize and Cyjon's backslash launcher are powerful but undiscoverable. Add hints, menus, and onboarding.
- **Full-frame busy loops:** TacOS's redraw model wastes resources and obscures frame scheduling. Use damage, callbacks, deadlines, and idle sleep.
- **Branding mistaken for system UI:** Nyaux's boot background is valuable but not a desktop capability.
- **Diagnostic catalog mistaken for apps:** RustOS's qualification entries should live in Developer Tools, not inflate the consumer launcher.

### 11. Delivery and proof plan

#### Stage A — contracts and reference targets

- freeze the component/service boundaries above;
- define app manifest, UI semantics, action, capability, and compositor protocols;
- produce a visual north star for shell, launcher, Files, Browser, Settings, and agent permission flow;
- lock initial tokens and accessibility requirements;
- define artifact/evidence schema.

Exit evidence: protocol examples, invalid-input tests, visual reference screenshots, token contrast audit, and an app-registry validator.

#### Stage B — compositor and shell vertical slice

- one native app plus one deliberately crashing client;
- surface attach/damage/frame callbacks;
- focus/drag/eight-edge resize/minimize/maximize/snap/close;
- taskbar, launcher/search, quick settings, notifications, keyboard navigation;
- crash and dead-app handling;
- capture exact screenshots from QEMU.

Exit evidence: input tests, frame pacing distribution, no busy idle loop, buffer lifecycle tests, crash isolation, keyboard-only workflow, and visual comparison.

#### Stage C — shared UI and core apps

- semantic widgets, text shaping, localization, accessibility tree;
- Files, Terminal, Settings, Activity, Text/Notes, Help;
- file handlers, clipboard, drag/drop, permission broker;
- generated menus from installed registry.

Exit evidence: each launcher opens; every Settings control reads back effective state; destructive file operations recover through Trash; screen-reader tree snapshots; RTL and non-Latin shaping screenshots.

#### Stage D — browser and networked workflows

- isolated renderer and network broker;
- navigation/forms/CSS/script/storage/downloads;
- browser accessibility tree and semantic agent bridge;
- crash/timeout/quota/security UX.

Exit evidence: standards-feature matrix with explicit unsupported states, origin/CORS/cookie tests, malicious parser corpus, renderer crash recovery, back/forward/reload, keyboard and screen-reader flows, downloaded-file provenance.

#### Stage E — agent composition and broad catalog

- agent broker, capability prompts, progress/cancel, receipts;
- app actions for Files/Browser/Settings/Text and system status;
- media/personal/document/dev/game families;
- external/ported app labeling and store/package transactions.

Exit evidence: intent→plan→bounded execution→deterministic check→independent review→receipt for every representative workflow; revocation tests; cancelled-operation cleanup; no remote/external side effect without authorization.

#### Stage F — hardware and release qualification

- multiple resolutions/DPI/input devices;
- cold/warm boot and persistence;
- GPU and software fallback;
- unplug/replug, network loss, disk full, low memory, app crash storms;
- physical-machine input/display/storage/network proof.

Exit evidence must separate build/host tests, QEMU graphical proof, and physical hardware. “Looks correct in a static image” cannot substitute for input, persistence, timing, error recovery, or hardware receipts.

### 12. Definition of done for any visible feature

A visual/app/browser feature is done only when all of these are true:

1. source exists in the owned boundary;
2. it is included in the actual build artifact;
3. launcher/action metadata resolves to that artifact;
4. its normal workflow completes;
5. empty, loading, busy, error, offline, permission-denied, and crash states are designed;
6. keyboard and accessibility semantics work;
7. at least one deterministic test or probe remains runnable;
8. QEMU screenshot/input evidence is tied to the exact artifact;
9. hardware is claimed only after hardware observation;
10. external code/content is labeled;
11. unsupported subfeatures return explicit errors;
12. the orientation/feature documentation links the receipt.

That definition is the practical synthesis of the entire shelf: the ideas are abundant; trustworthy reachability and product truth are scarce.
