# zlOS initialization registry truth

The machine-readable authority is
[`../init-registry.json`](../init-registry.json), generated by
[`../gen-init-registry.py`](../gen-init-registry.py). It records the actual
top-level boot order in `kernel.zl`; it is not a proposed service graph.

## Current graph

Sixteen ordered stages cover baseline keyboard/filesystem/settings state,
display policy, compositor admission, GDT, IDT/PIC/PIT/PS2, optional APIC,
USB, program arena, heap, virtual-memory report, Ring-3 smoke proof,
application manifest, build identity and final readiness publication.

Every stage records:

- its exact source anchor and current line;
- owner and earlier-stage dependencies;
- whether success, an attempt, optional data/provider behavior or a runtime
  proof is required;
- the current failure/fallback behavior;
- all six promoted QEMU boot routes;
- the evidence ceiling.

This makes an important distinction explicit: all six routes reaching the
later ready and identity markers proves the ordered path stayed bootable. It
does not prove every provider succeeded, and it is not physical-hardware
evidence. APIC may retain PIC, settings may retain defaults, and unsupported USB
hardware may retain fallback input without falsifying the source order.

## Fail-closed checks

The generator refuses stale source, artifact/build identity disagreement,
missing or duplicated routes, missing/reordered stages, and dependencies that
do not name an earlier stage. Its self-test plants missing-stage,
reordered-stage, unknown-dependency and missing-route mutations.

The landing gate writes and then checks this registry only after the exact
artifact, boot-route and application evidence registries pass. Deleting the
generator or either landing invocation is itself a gate failure.

## Known architectural gap

This registry exposes rather than hides the current weakness: several legacy
initializers return no typed status, initialization policy still lives in the
monolithic kernel, and rollback/teardown is not a general protocol. Later
MP phases replace those calls with versioned descriptors, dependency admission,
bounded start/abort, health receipts and reverse-order shutdown. Until then,
this file is the exact baseline that migration must preserve.
