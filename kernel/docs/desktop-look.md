# Why zlOS looks blocky — and why it mostly doesn't

The question: *"how does Windows look so good compared to ours looking blocky?"*

Answered by reading the code, 2026-08-17. The short version is that **the
renderer is not the problem** — it is already close to modern. The gap is in the
assets and the grid, and three specific bugs.

---

## First: what is already good

Do not rebuild any of this. It exists and it works.

| Already in the kernel | Where |
|---|---|
| **Real TrueType glyphs** — DejaVu Sans Mono, FreeType-hinted | `font_aa.c`, generated by `gen_hd_font.py` |
| **Subpixel LCD rendering** — three alphas per pixel, 5-tap (1,2,3,2,1)/9 FIR to kill colour fringing | `font_sub.c`, `fb.c:243` `blend_sub` |
| **Gamma-correct blending in linear light** — two lookup tables built at boot, no floating point | `fb.c:195-273` |
| **Dithered gradients** — ordered 4×4 threshold, so bands dissolve instead of stepping | `fb.c:459-512` |
| **Anti-aliased rounded corners** — 4×4 supersampled coverage per corner pixel | `fb.c:620` `fb_rrect` |
| **Soft shadows** — chebyshev distance falloff, one pass per pixel, no ringing | `fb.c:574` `fb_shadow` |
| **Icons as geometry** — drawn at 96×96 and box-filtered to 24×24, so they are shapes not pictures | `gen_icons.py` |

That is a serious rendering stack. Gamma-correct linear-light text blending in
particular is something a lot of shipping commercial software still gets wrong.

**The renderer is roughly 90% of the way to modern.** Keep that in mind before
concluding anything looks bad because of how it is drawn.

## What is actually blocky — three concrete bugs

### 1. Icons are destroyed on every real screen

`fb.c:929`, inside `fb_icon24`:

```c
int a = ic[y / sc][x / sc];
```

That is **nearest-neighbour upscaling.** `sc` is `cell_w / GLYPH_W`, which is 2
on any screen 1400px or wider — i.e. every screen actually used.

So the pipeline is: draw the icon as clean geometry at 96×96 → box-filter it down
to 24×24 → **blow it back up to 48×48 by copying each pixel into a 2×2 block.**

All the anti-aliasing is thrown away. Every icon in the dock, the start menu and
the tray is chunky squares. **This is the single most visible source of
blockiness in the whole desktop.**

**Fix, easiest first:**
- Regenerate the atlas at 48×48. `gen_icons.py` already draws at 4× — it just
  needs a different output size. Roughly a one-line change.
- Or interpolate between source pixels in `fb_icon24` instead of copying.
- Best: keep the geometry and rasterize at the size actually needed.

### 2. Lines have no anti-aliasing

`fb.c:669`, `fb_line`, is plain integer Bresenham — a hard on/off pixel per step.

The System Monitor sparkline (`kernel.zl:1650-1657`) is eight diagonal segments,
and every one staircases. It sits directly beside beautifully anti-aliased text,
which makes it worse, not better — the contrast draws the eye to it.

**Fix:** Wu's line algorithm. About 20 lines, and `blend_rgb` already exists to
do the blending.

### 3. The logo path draws solid squares

`fb.c:515` `fb_glyph_scaled` reads the **1-bit** `font8x16` — not the coverage
atlas — and draws each set bit as a filled `scale × scale` rectangle. Reached
from zl via the `logo()` builtin.

That is the blockiest drawing path in the codebase, and it is the one used for
the largest text on screen.

**Fix:** draw scaled text from the coverage atlas via `fb_text_aa2x`, or
regenerate a larger atlas. `text_big` already does the right thing — `logo` is
the odd one out.

## What is not a bug, but is why it reads "terminal"

### Text is locked to the cell grid

`fb_text_aa` (`fb.c:355`) advances by exactly `cell_w` per character — 8px or
16px. So **every string on screen is monospace-positioned**, including window
titles, dock labels and the System Monitor's readouts.

Nothing is wrong with the glyphs. They are correct and smooth. But uniform
advance is the single strongest visual signal of "this is a terminal", and it is
applied to parts of the UI that are not a terminal.

**Fixed 2026-08-18** — but not the way this said, and the correction is the
interesting part.

This proposed emitting per-glyph advance widths from the existing atlas.
**That alone does nothing.** The atlas font is DejaVu Sans **Mono**: every
advance FreeType reports for it is the same number, so the table would have
been 95 copies of one value and the screen would not have moved a pixel. The
plan was right about the mechanism and wrong about the data.

Real proportional text needs a proportional **face**. `gen_prop_font.py` emits
a second atlas from DejaVu **Sans** — the proportional cut of the same
superfamily, same designer, same shapes — with per-glyph advances:

| | cell | advances | distinct values |
|---|---|---|---|
| body | 16×16 at 15px | 4–15 | **12** |
| title | 30×32 at 29px | 8–29 | **20** |

12 and 20, against the 1 and 1 the mono font would have given. That number *is*
the feature.

On "no new fonts": the rule's intent is not to introduce a second visual
system, and the proportional cut of the same family is not one. The console
keeps its grid and keeps the mono atlas — exactly the split this section asks
for. Only titles, labels, buttons, list rows and tab captions change.

Two details that are easy to get wrong:

- **The cell is wider than the advance.** A proportional glyph can overhang the
  advance it hands on (`m`, `W`) and can start left of the pen. The cell holds
  the widest *ink* box so nothing is cropped, while the pen still moves by the
  real advance. Cropping to the advance is the classic way round letters end up
  clipped.
- **Anything centred or right-aligned must now measure.** `ui.c`'s `text_w()`
  was `length × cell_w`; it is `fb_text_prop_w()` now, and that one change
  reaches every widget.

### UI scale is 1× or 2×, nothing between

`fb.c:143` — `cell_w = (width >= 1400) ? GLYPH_W * 2 : GLYPH_W`.

A binary switch. There is no 1.25× or 1.5×. Everything is integer-doubled, which
is why a 2560×1440 panel gets the same UI as 1920×1200, just larger.

Not urgent. Worth knowing when the ThinkPad panel is in play.

## What Windows actually has that we don't

Mostly **not** rendering technology.

| | Windows | zlOS |
|---|---|---|
| **Icons** | thousands, vector or at every size | 10, at one size, upscaled badly |
| **Type** | many sizes, several weights, proportional | 2 sizes (13px, 26px), 1 weight, monospace |
| **Spacing** | a scale everything snaps to | hand-picked per window (`14 * u` here, `56 * u` there) |
| **Scaling** | 100/125/150/175% | 1× or 2× |
| **Decisions** | a design team argued over every pixel | one person, in between writing a DPLL driver |

The last row is the real one and it is not a criticism. The look zlOS already has
is coherent — deep navy, nested rounded panels, focused-blue title gradients with
an accent underline, soft shadows. That is a deliberate aesthetic, closest to
BeOS/NeXT. It does not need replacing. It needs its own rules applied
consistently, and the three bugs above fixed.

---

## Ranked by improvement per unit of effort

1. **Fix the icon upscale.** Biggest visible win in the entire list, smallest
   change. Do this one first.
2. **Anti-alias `fb_line`.** ~20 lines, removes the one jagged thing sitting next
   to smooth text.
3. **Fix the `logo` path** to use the coverage atlas.
4. **Proportional advance for UI labels** (not the console). This is the one that
   stops the desktop reading as a terminal.
5. More icons, more type sizes, a spacing scale.

Items 1–3 are bug fixes and could be done in an afternoon. Item 4 is a feature.

---

## Rules for anything new

- Never introduce a second visual system. Extend the one that exists.
- No generic flat/material look. This is a hand-built OS with a real aesthetic.
- Focus is signalled by title-bar hue **plus** the accent underline. Both already
  exist. Do not add a third signal.
- No new fonts, no new corner radii. Nested 5px/4px `rrect` and `TITLE_H 28` are
  the system.
- If something looks bad, **check whether it is a resampling bug before blaming
  the renderer.** That was the lesson of this whole document.
